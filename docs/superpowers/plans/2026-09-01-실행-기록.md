## Task 6을 시작하기 전에 반드시 할 것

1. **`vitest.config.ts`의 `__dirname`을 먼저 고친다** — 계획의 Task 6 Step 0. Task 1~5는 상대 경로만 써서 `@/` alias를 타지 않았지만 Task 6부터는 쓴다. `__dirname`은 네이티브 ESM에서 undefined이고 지금은 Vite 설정 로더의 CJS shim 덕분에만 동작한다. 깨질 때까지 기다리면 alias를 쓰는 모든 테스트가 한꺼번에 무너진다.
2. **Task 4B를 Task 8보다 먼저 한다** — 계획에 신설된 태스크. 실제 네이버폼 다열 엑셀에서 셀러 이름이 망가지는 실제 결함이다.

## 이연한 지적 (최종 리뷰가 "그냥 둠"으로 분류)

브랜치 전체 리뷰가 이연 항목 18건을 분류했고, "머지 전 필수"는 1건뿐이었다(금지어 테스트 확장 — `6c5ab4e`로 처리). 나머지는 아래와 같이 남아 있다. 고칠 의무는 없지만 해당 파일을 만질 때 함께 처리하면 좋다.

**`src/domain/phone.ts`**
- `phone.ts:12`의 `(raw ?? '')`는 `raw: string` 타입 아래서 도달 불가한 죽은 코드
- `formatPhone`에 길이 검사가 없어 11자리가 아닌 입력에 잘못 묶인 결과를 조용히 낸다. 현재 두 호출부 모두 정규화된 값을 넘기므로 선행조건은 성립
- 구형 011/016/017 접두는 테스트에 없다. 한국은 2G가 종료되어 `010`만 다루는 것이 옳다

**`src/domain/roster.ts`**
- `seen`이 `Map<string, number>`인데 저장한 줄 번호를 읽지 않고 `.has()`만 쓴다. `Set<string>`이 의도를 더 잘 표현한다
- `parseRosterCells`의 issue 보고·중복 경로와, 빈 줄/머리글이 오류 행보다 앞설 때의 줄 번호가 테스트로 고정되지 않았다

**`src/domain/xlsx-roster.ts`**
- `xlsx-roster.ts:34`가 빈 시트에 `{rows:[],issues:[]}`를 하드코딩한다. `parseRosterCells([])`를 부르면 빈 입력 계약이 바뀌어도 갈라지지 않는다
- `cellText`의 Date·richText·formula 분기가 테스트되지 않는다. 네이버폼 다운로드에 제출시각 컬럼이 있으면 Date 셀이 실제로 나온다
- 이 파일은 사실 도메인 로직이 아니라 **어댑터**다. `exceljs`를 `src/domain/`에 끌어들이고 `parseXlsxRoster`를 async로 만들어 호출부까지 번진다. `src/domain/adapters/`로 옮기면 "순수 도메인" 주장이 정직해진다

**`src/domain/template.ts`**
- 수정된 `renderTemplate`의 `key: '이름' | '링크'` 주석은 `as` 캐스트가 아니라 replacer의 `any[]` 인수를 문맥상 받는 것이다. 나중에 정규식에 그룹이 추가되면 이 주석이 조용히 틀리게 된다
- 이모지(BMP 밖 문자)를 2바이트로 센다. EUC-KR은 이모지를 인코딩할 수 없어 솔라피가 길이와 무관하게 다른 타입으로 처리할 수 있다. 과대 계산이라 안전한 방향으로 실패한다
- `messageType`의 90바이트 경계는 KISA/CP949 표준과 스펙의 "한글 45자"에 부합하지만, 솔라피의 실제 자동 전환 동작과 대조된 적이 없다. Task 9~10에서 실제 API로 확인할 것

**빌드·의존성**
- `npm test` 출력에 Vite의 "CJS build of Vite's Node API is deprecated" 경고. vitest 3으로 올려야 사라진다
- `exceljs` 4.4.0이 deprecated 전이 의존성(fstream, glob@7, inflight, rimraf@2, uuid@8)을 끌어와 install 시 경고가 난다. 쓰기·zip 경로에 국한되고 우리는 `load`만 쓴다
- `uuid@8.3.2`의 moderate 권고(GHSA-w5hq-g745-h8pq)는 v3/v5/v6에서 `buf` 인수가 주어질 때의 문제다. exceljs는 v4만 인수 없이 호출하므로 도달 불가
- `next`가 의존하는 `postcss` 권고는 next 메이저 업그레이드로만 해소된다. 빌드 시점에 우리 자신의 CSS를 처리하며 사용자 입력을 파싱하지 않는다
- `npm audit fix --force`를 실행하지 말 것. `exceljs@3.4.0` 다운그레이드를 제안한다

**Task 8에 미리 반영된 것** (계획 본문 참조)
- 손상된 엑셀 업로드를 500이 아니라 `issues` 통로로 흘려보낸다
- 업로드 크기 2MB 제한
- `result.issues`를 리다이렉트 URL에 실을 때 `raw` 길이를 항목별로 잘라야 한다. 20건이 각각 붙여넣은 줄 전체를 들고 있으면 쿼리스트링이 감당하기 어려워진다
- `parseXlsxRoster`의 인수 타입을 `Buffer | ArrayBuffer`로 넓히는 것을 검토할 것. 테스트가 Node `Buffer`를 `as ArrayBuffer`로 캐스팅하고 있어 시그니처가 약한 거짓말을 한다

## 실행 중에 내린 판정

계획에 없던 결정을 실행 중에 내렸다. 브랜치 전체 리뷰가 12건 전부를 검토해 **모두 SOUND**로 판정했으며, 3번과 6번에 단서를 달았다.

1. **worktree 대신 브랜치 `domain-logic`** — 병행 작업이 없고 두 번째 작업 디렉터리는 혼란만 준다
2. **계획의 "12 passed" 기대값은 오기, 실제 11** — 계획 작성 시 잘못 센 것
3. **`__dirname`을 Task 1~5에서는 그냥 둔다** — 이 다섯 태스크는 alias를 안 쓴다. **단서: Task 6 Step 0으로 올려 alias에 의존하기 전에 고칠 것.** "깨지면 그때"로 미루면 조용히 틀린 경로를 가리킨다
4. **담당자 실명을 `ADMIN_NAMES` 환경변수로** — 저장소가 공개라 실명이 영구 검색 가능해지고, 담당자 교체 시 코드 수정이 필요해진다
5. **미추적 빌드 산출물을 컨트롤러가 직접 `.gitignore`에 추가** — 프로세스 이탈이지만 내 커밋을 리뷰 범위에 포함시켜 판단받았다
6. **`next-env.d.ts`를 무시하지 않고 커밋** — `tsconfig.json`의 `include`가 이름으로 명시하므로 무시하면 새 클론에서 `npm run typecheck`가 TS6053으로 실패한다. **단서: 생성 파일을 커밋하는 것은 다소 이례적이다**
7. **`uuid@8.3.2` 권고 수용** — 취약 함수 계열(v3/v5/v6)을 아예 쓰지 않아 도달 불가
8. **`postcss` 권고 수용** — 빌드 시점 전용, 사용자 입력을 파싱하지 않는다
9. **손상된 엑셀 업로드를 `issues` 통로로** — Task 8이 그대로 재현할 500 에러를 계획 단계에서 차단
10. **`renderTemplate` 치환 비안전성을 이연하지 않고 수정** — `이름`은 담당자가 붙여넣은 임의 텍스트이고, 실패하면 실제 셀러에게 깨진 문자가 조용히 발송된다. 스펙이 요구하는 것은 "올바른 치환"이지 `replaceAll` 자체가 아니다
11. **최종 브랜치 리뷰를 opus 대신 sonnet으로** — opus가 세션 한도에 걸려 사용 불가했다. opus 한도가 풀린 뒤 같은 범위(`f2b47c8..6c5ab4e`)로 다시 돌릴 수 있다
12. **엑셀 파서를 `xlsx`에서 `exceljs`로 교체** — 사용자에게 세 선택지를 제시해 선택받았다. npm의 `xlsx`는 0.18.5에서 버려졌고 프로토타입 오염·ReDoS 권고가 있으며 수정판이 npm에 없다

## 이 실행의 성격

각 태스크를 구현한 에이전트와 리뷰한 에이전트를 분리했고, 리뷰가 실제로 결함을 잡았다:

- 내가 `.gitignore`에 `next-env.d.ts`를 넣어 만든 typecheck 함정
- `renderTemplate`의 치환 비안전성 — 내가 계획에 쓴 코드의 결함
- 손상된 엑셀 업로드가 Task 8에서 500이 되는 위험
- **네이버폼 다열 엑셀에서 셀러 이름이 망가지는 결함** — Task 3 설계가 2열 입력을 암묵적으로 가정했고, 내가 쓴 테스트도 전부 2~3열이어서 자체 검토로는 잡히지 않았다
